# Автоматизация локальной разработки: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Обеспечить удобный Docker Compose dev-режим и воспроизводимые локальные проверки, совпадающие с CI.

**Architecture:** Сохранить существующий Compose и production-образы; дополнить их отдельной dev-конфигурацией с локальными PostgreSQL и Redis, подключением исходников и перезагрузкой. Команды проверок запускать в контейнерах и использовать их же в CI.

**Tech Stack:** Docker Compose, Python 3.12, pytest, Ruff, Node.js, Vite, React, GitHub Actions.

**Spec:** Согласованное в беседе описание: локальные PostgreSQL и Redis, горячая перезагрузка, общие проверки с CI; облачные инстансы VK Cloud не участвуют в обычной локальной разработке.

## Global Constraints

- Не менять production-поведение Dockerfile и базового Compose без необходимости.
- Не удалять и не пересоздавать PostgreSQL volume автоматически; не перезаписывать существующий `.env` без явного запроса.
- Не выдавать миграции, seed, готовность к подключению к БД или Celery broker за реализованные функции.
- Не выводить секреты в диагностике и CI-логах.

## Review Focus

- Существующий `.env`: обычный запуск и генерация не изменяют его.
- Существующий volume PostgreSQL: смена `.env` не предполагает автоматическую смену пароля БД и не удаляет данные.
- Запуск из произвольного каталога: `scripts/dev.sh` использует корень репозитория.
- Изолированные проверки: команды работают без уже запущенного стека и реальных секретов.
- Dev-прокси и hot reload: запросы `/api/` и `/ingest/` сохраняют поведение nginx; изменения backend и web становятся видимыми без пересборки.

### Task 1: Согласованная локальная конфигурация

**Files:** Modify: `scripts/dev.sh`, `.env.example`; Test: `tests/test_dev_script.py`.

**Interfaces:** `./scripts/dev.sh env [--force]` создаёт `.env` с уникальными секретами; пароль в `DATABASE_URL` совпадает с `POSTGRES_PASSWORD` для вновь сгенерированной конфигурации.

- [ ] Добавить тесты генерации в изолированной копии: пароль и URL согласованы, секреты непустые, права `0600`, существующий файл без `--force` не изменён.
- [ ] Запустить тесты и убедиться, что тест согласованности падает на текущем скрипте.
- [ ] Исправить генерацию так, чтобы один пароль использовался для обеих переменных; не выводить секреты.
- [ ] Повторить тесты; документировать, что `--force` не меняет пароль в существующем volume и требует отдельной ручной процедуры.

### Task 2: Dev-режим сервисов

**Files:** Create: `docker-compose.dev.yml`; Modify: `scripts/dev.sh`, `services/web/vite.config.js`, при необходимости dev-стадии Dockerfile; Test: `tests/test_dev_config.py`.

**Interfaces:** `./scripts/dev.sh up` запускает dev-конфигурацию; web доступен на `localhost:8080`, API на `8000`, ingest на `8001`; `down`, `logs`, `status`, `config`, `restart` используют тот же набор Compose-файлов.

- [ ] Добавить проверки разрешённой конфигурации и команд: dev-тома, uvicorn `--reload`, Vite dev server и маршруты прокси соответствуют `services/web/nginx.conf`; базовый Compose не меняется.
- [ ] Запустить проверки и зафиксировать исходное падение.
- [ ] Добавить dev-конфигурацию с монтированием исходников, автоматическим обновлением API/ingest и Vite, изоляцией `node_modules` в контейнере; сохранить базовую конфигурацию пригодной для production-подобной сборки.
- [ ] Проверить `docker compose ... config`, запуск стека и доступность endpoint'ов; изменить исходники временно, проверить reload и вернуть только собственные изменения.
- [ ] Не утверждать, что Celery автоматически подключён к Redis или перезагружается, пока это отдельно не реализовано.

### Task 3: Проверки для локальной работы и CI

**Files:** Modify: `Makefile`, `.github/workflows/pr.yml`, `services/web/package.json`, `services/web/Dockerfile`; Create: lockfile и необходимые конфигурации/тесты web, контейнерная конфигурация проверок; Test: `tests/test_dev_checks.py`.

**Interfaces:** `make test`, `make lint` и `make check` запускаются через Docker без работающего стека; CI запускает те же команды; `make helm-lint` остаётся отдельным.

- [ ] Добавить тесты/проверки наличия обязательных команд web и того, что CI не использует `--if-present` для lint/test; убедиться, что текущая конфигурация их не проходит.
- [ ] Зафиксировать версии dev-зависимостей Python и web и добавить npm lockfile; production web-сборка использует `npm ci`.
- [ ] Добавить реальные web lint и тест рендеринга scaffold, backend pytest/Ruff и Compose config validation в воспроизводимые контейнерные команды; `make check` запускает все обязательные проверки и возвращает ненулевой код при любой ошибке.
- [ ] Обновить PR workflow для вызова этих команд; отдельные Helm и security jobs сохранить.
- [ ] Запустить общие команды локально; убедиться, что поломанный тест и ошибка lint действительно приводят к ошибке, не оставляя намеренных поломок.
